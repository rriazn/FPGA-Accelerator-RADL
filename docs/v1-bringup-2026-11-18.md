# v1 accelerator on the ZedBoard: bring-up report (2026-11-18)

Follow-up with the new address generation (2026-11-25): section 11.

Written for the team (Roman, Olimjon) and as a source for the report and the presentation. It records what was done on the way from "simulated in GHDL" to "network runs bit-exact on the board", what went wrong, the commands that worked, and what is still open. Numbers marked *measured* come from the board; numbers marked *arithmetic* are computed from measured ones; anything marked *(check)* was not confirmed.

## 4. How the day went (order of events)

1. **Block design started for the Ultra96** (the Vivado part used was the ZU3EG, `BOARD := ULTRA96`). Address Editor: `s_axi` at `0x8000_0000`, `HP0_DDR_LOW` at `0x0000_0000`, `HP0_LPS_OCM` at `0xFF00_0000`.
2. **Timing on that build:** at 100 MHz about 15 ns too slow, worst path from `u_regs/s_regs_reg...` to `u_engine/u_core/s_out_addr_d1_reg` (section 6).
3. **Board check:** `docs/connect-to-board.md` describes the ZedBoard, not the Ultra96, and the lab has only the ZedBoard. The Ultra96 bitstream cannot run on it. The block design was redone for the Zynq-7000 (section 5, new project). The Ultra96 project is kept for later.
4. **ZedBoard build:** target 25 ns (40 MHz), worst path about 79 ns. Decision: keep the RTL, run at **10 MHz** (option "only lower the clock"). The address-generation rewrite is deferred.
5. **Board session:** boot setup, network, bitstream, clock, probe, golden layers, whole network (section 7).

## 5. Problems in Vivado and what fixed them

| What happened | Cause | Fix |
|---|---|---|
| `[Place 30-415] IO Placement failed ... 502 I/O ports ... 297 available` (2026-11-11) | the top was implemented on its own: Vivado treated the AXI ports as real pins and added I/O buffers | not a design error; use the block design, or synthesize out of context (`-mode out_of_context`) and do not implement |
| Add Module: `conv_accel_top` incompatible, `[IP_Flow 19-627] ... Undefined parameter "AXI_DATA_W"`, `[IP_Flow 19-1816] Address Space 'm_axi': Invalid addressSpace width value ""` (2026-11-11) | Vivado reads the ports of a module reference without the packages, so widths from `camus_pkg` are unknown | thin wrapper with literal widths and no generics: `conv_accel_bd_zed.vhd` / `conv_accel_bd.vhd`; if the widths do not match `BOARD` the wrapper does not compile (checked in GHDL for both boards) |
| "Cannot generate bitstream for out of context modules" | the project still had `-mode out_of_context` and the OOC XDC from the standalone timing run | remove the option, remove or disable `conv_accel_top_ooc.xdc`, top = the block design wrapper |
| Wrapper marked invalid after all sources were set to VHDL 2008 | not found out why | set everything to VHDL 2008 **except the wrapper**, which stays plain VHDL (worked). Only 2008 construct GHDL reported in the sources is `process(all)` in `axi_master_rd.vhd`; an experiment to remove it was reverted and was not needed |
| Warnings "parameters have negative values" on the ZYNQ7 PS | most likely the DDR board delay values (negative by design in the ZedBoard preset) *(check)* | ignored, the DDR and MIO setup comes from the boot image on the SD card, not from the bitstream |
| Timing: 25 ns target, about 79 ns actual (ZedBoard); about 15 ns over at 100 MHz (Ultra96) | `addr_gen` computes addresses with divisions by run-time values (`out_dim` by stride, `elem_addr` by the lane count) and three chained 32-bit multiplications, all in one clock | PL clock 10 MHz for now; real fix open (section 9) |

The constraint file was never the problem: the block design needs none (the PS block brings the clock constraint, the accelerator has no pins).

## 6. Block design that worked (ZedBoard)

- Top module `conv_accel_bd_zed` (module reference); all sources VHDL 2008 except that wrapper; `-bin_file` in the bitstream settings.

The full step list is `docs/plans/vivado-block-design.md`.

## 7. Board session: what worked, in order

PC is Windows. The board boots from the SD card into U-Boot, then Linux in RAM (`init=/bin/sh`).

1. **Boot lines in U-Boot** (Enter right after Reset to catch the 3 second countdown):
   ```
   setenv initrd_high 0xffffffff
   setenv fdt_high 0xffffffff
   setenv bootargs console=ttyPS0,115200 rdinit=/bin/sh init=/bin/sh mem=496M
   boot
   ```
2. `mount -t proc proc /proc`, `mount -t sysfs sys /sys`, `mount -t devtmpfs devtmpfs /dev`, `ifconfig eth0 192.168.1.10 netmask 255.255.255.0 up`.
3. Checks: `cat /proc/cmdline` contains `mem=496M`; `grep MemTotal /proc/meminfo` below 507904 kB (it showed 513200 kB when `mem=` was missing).
4. Files from the PC with `python -m http.server 8000 --bind 192.168.1.1 --directory build` and `wget`: `board-accel.tar.gz` (`make package-accel`) and the bitstream `.bin`. Windows needed an address on the adapter and a firewall allowance for the board (see section 8).
5. Bitstream: `cat <file>.bin > /dev/xdevcfg`, then `cat /sys/devices/soc0/amba/f8007000.devcfg/prog_done` must print `1`.
6. PL clock: `echo fclk0 > /sys/devices/soc0/amba/f8007000.devcfg/fclk_export`, `cat /sys/class/fclk/fclk0/set_rate` printed 99999999, then `echo 10000000 > /sys/class/fclk/fclk0/set_rate`.
7. Run (in the unpacked `c/` folder):
   ```
   ./armhf/accel_probe --regs 0x40000000 --mem 0x1F000000:0x1000000
   ./armhf/accel_golden ../build/export b3sc --regs 0x40000000 --mem 0x1F000000:0x1000000   # and the other layers
   ./armhf/camus_accel ../build/export 2 --regs 0x40000000 --mem 0x1F000000:0x1000000
   ```

## 8. Things that cost time (lessons)

- **The Vivado PS settings are not applied by the bitstream.** On the Zynq-7000 the boot image on the SD card sets clocks and PS interfaces. The lab image runs `FCLK_CLK0` at 100 MHz, so the clock has to be set from Linux before using the accelerator. Run it at no more than the clock the bitstream was built for.
- **`mem=496M` alone makes the boot panic** (`VFS: Unable to mount root fs`): U-Boot moves the ramdisk to the top of RAM, above the 496 MB the kernel may now use, and the kernel drops it. `initrd_high` and `fdt_high` = `0xffffffff` keep them in place. The reason is the likely one, the kernel's `initrd extends beyond end of memory` line was not looked at.
- **Reserve the DMA memory before using it.** Root file system and `/tmp` are in RAM; memory the kernel still owns can hold your files, and the accelerator writing there would corrupt them.
- **A register read without bitstream or PL clock hangs the board** (`Ctrl+C` does not work in this shell, only Reset). Load the bitstream and check the clock first.
- **`--mem 0x1F000000:01000000` is octal** (a leading zero): 256 KB. Enough for `accel_probe`, not for the big layers or `camus_accel`. Write `0x1000000`.
- **Windows:** the board's `ping` to the PC fails by default because the firewall blocks ICMP echo, and `wget` to `python -m http.server` is blocked on a "Public" network (a direct cable is an unidentified network). Ping the board from the PC to test the link, and allow TCP 8000 and ICMP echo from `192.168.1.10` only (rules removed afterwards).
- A boot banner "Coordinate server / Board IP 169.254.134.200 / Waiting for PHY autonegotiation" appeared once; it is not our software. How it was resolved was not recorded.
- At 10 MHz one frame takes about 3 minutes, so use 1 or 2 frames with `camus_accel`, not 200.

## 9. Open

1. **Address generation (timing).** Precompute the per-layer constants at start and make each address from running counters (no division, no chained multiplications). It would allow a much higher clock. Decision 2026-11-18: not now. Open choice: hardware precompute vs. OH/OW registers filled by the driver (the second changes the register map). **Update 2026-11-20:** hardware precompute chosen and implemented in simulation, see [addr-gen-rewrite.md](plans/addr-gen-rewrite.md); Vivado and board still to do.
2. **DDR waiting.** 47 clocks per MAC, from single-beat reads one at a time. Plan steps 4.1 onward (line buffers, bursts, weights in BRAM). Fixing only the clock would give about 17 s per frame at 100 MHz (*arithmetic*), far from 33 ms.
3. **Energy per frame:** not measured (needs the power meter and a long run, idle reading first).
4. **Not recorded:** CYCLES of the nine `accel_golden` layers, Vivado version, WNS/TNS and resource use of the bitstream, which `.bin` format worked (Vivado `-bin_file` output or bootgen), how the first network problem on Windows was solved.
5. **Process:** the PS configuration of the block design is not what the board runs. If a clean setup is wanted, build the boot image (FSBL, U-Boot) from the exported hardware instead of relying on the lab SD card.
6. **Ultra96 (later, final target):** the Ultra96 project exists (`conv_accel_bd`, `BOARD := ULTRA96`, 128 bit, `s_axi` at `0x8000_0000`), it was not tried on a board. It needs 64-bit programs (`make package64`).
7. **Old technical debt** that still applies: the soft reset pulse is not wired to the masters (TD-3); a layer that hangs can only be recovered by reloading the PL or resetting the board.

## 11. Update 2026-11-25: new address generation, faster clock

What changed: `addr_gen` now makes its addresses from running pointers and per-layer constants (`layer_setup`), so the 79 ns path of section 5 is gone ([plans/addr-gen-rewrite.md](plans/addr-gen-rewrite.md)). Commit `ee7e33a`. Register map and ARM software are unchanged.

| Run | PL clock | Frames | Wall time per frame | Accelerator clocks per frame | Clocks per MAC |
|---|---|---|---|---|---|
| 2026-11-18, old RTL | 10 MHz | 2 | 176.542 s | 1,764,192,598 | 47.2 |
| 2026-11-25, new RTL, 70 MHz requested | about 66.7 MHz (not read back) | 2 | 33.803 s | 2,245,340,565 | 60.1 |
| same | same | 5 | 33.803 s (mean 33,802.861 ms, min 33,802.670, max 33,803.083) | 2,245,339,410 | 60.1 |

All three runs are bit-exact (0 of 2, 0 of 2, 0 of 5 frames differ). Frame time improved 5.2 times (176.5 s to 33.8 s); against the naive C `-O2` (1.376 s on the same board) v1 is now about 25 times slower (arithmetic).

**Clock on the board.** The PL clock request is rounded by the kernel to what the IO PLL dividers give (1000 MHz divided by an integer). A request of 70 MHz probably gave 66.7 MHz (2,245,340,565 clocks in 33.68 s, which is the wall time minus about 0.12 s of ARM steps, is 66.7 MHz), a request of 75 MHz probably 71.4 MHz. The bitstream passed `accel_probe` at 10, 50 and 75 MHz, but at a 75 MHz request the whole network failed in layer `b2c2`, and one probe run at a higher clock failed on all five layers (`accel_run returned -3`, the STATUS error flag; the clock of that run was not recorded). So the limit of this build lies between about 66.7 and 71.4 MHz, which is marginal. The `set_rate` values were not read back and written down, do that from now on.

**Why the clocks per MAC went up.** Not the rewrite: in simulation with an idealized memory the old and new RTL need the same clocks (tiny_a 94,874 and 94,886, tiny_b 454,190 and 454,198, tiny_e 2,624 and 2,634). On the board the memory wait is a fixed time, so a faster clock spends more clocks on it. A two-point fit gives about 45 clocks of logic plus about 230 ns of memory wait per MAC (rough). Consequence: a faster PL clock helps less and less, extrapolating about 25 s per frame at 100 MHz and about 17 s at 200 MHz (not measured). The way down is fewer waits for DDR (bursts, line buffers, weights in BRAM: plan steps 4.1 onward), not only a higher clock.

**The Vivado timing of these builds is not verified.** The PS block generated a 100 ns clock constraint although `FCLK_CLK0` was set to 75 and 100 MHz (cause not found; PS setting, Validate Design, regenerating output products and resetting the runs did not help). The implementation was never asked to be fast, and the reported "longest path of about 9 ns" is not a result for 100 MHz. A workaround constraint exists (`vhdl/constraints/zed_fclk0_override.xdc`, not run in Vivado yet).

**Open after this update**
1. A build whose Timing Summary (the report file of the run) shows the target period with WNS >= 0, then the real limit and the next critical path.
2. `set_rate` read back after every setting, and the real clock written next to each result.
3. The question of where the 100 ns constraint comes from (see `plans/vivado-block-design.md` section 5).
4. DDR waiting as the main cost: plan steps 4.1 onward.
5. Energy per frame is still not measured (power meter).
6. Items from section 9 that are still not recorded: the CYCLES of the nine `accel_golden` layers, the Vivado version and the resource use.
